# 放置策略决策记录（ai-strategy）

> 负责人：ai-strategy　｜　范围：`classify.py` / `rules.py` / `store.py` / `planner.py`
> 所有决策由本角色自主做出，未采用本地神经网络模型。原因见第 1 节。

---

## 1. 为什么不用本地 LLM / 神经网络

这是本模块最关键的取舍，结论：**规则引擎优先，模型仅在明确需要时作为可选增强，且默认关闭**。

| 维度 | 本地小模型 | 规则引擎（本实现） |
|---|---|---|
| 体积 | 量化后的 1B~3B 模型约 0.6~2 GB，随包分发会让工具从「一个绿色 exe」变成「一个安装器」 | 约 30 KB 源码，零数据文件 |
| 冷启动 | 首次加载权重需 1~5 秒（磁盘慢时更久），每次启动都要付 | 常量表加载，微秒级；单文件分类 < 0.1 ms |
| 离线可靠性 | 依赖 tokenizer / 推理库 / 特定 CPU 指令集；Windows 上还要处理 VC++ 运行库、模型路径、显存不足等失败面 | 纯标准库，无 ABI 风险，任何装得上 Python 3.10+ 的机器都能跑 |
| 可解释性 | 输出是概率，用户问「为什么把这张图放进重要」答不上来 | 每条 Proposal 都带 `reasons`，如「扩展名 .png → 图片」「命中规则 rule-screenshot」 |
| 可审计 / 可改 | 调参要重新训练或改 prompt，行为漂移不可控 | 规则是 JSON，用户能直接看、直接改、直接导出导入 |
| 正确性 | 对文件名这种短文本，小模型的分类精度未必优于扩展名映射；幻觉风险真实存在 | 扩展名映射近乎确定；边界情况交给规则与用户改判 |

**核心判断**：桌面整理是一个「错误成本高、正确性由确定性事实（扩展名、大小、修改时间、文件名关键词）主导」的任务。引入模型带来的复杂度（分发体积、启动延迟、失败模式、不可解释）与其边际收益不成正比。这不是「不会做模型」，而是**在给定约束下模型不是最优解**。

预留的演进位：`classify()` 的判定链是分层的（见第 3 节），未来若要接模型，只需在最前面插入一层「模型建议」，并把它的 `confidence` 压低（模型意见只作为候选，不直接覆盖规则），`Proposal` 结构不需要改动。

## 2. 规则引擎的分层策略

`classify(item, store)` 按**优先级从强到弱**依次判定，命中即返回：

```
1. 用户历史偏好（store.lookup）        confidence 0.95   ← 最高优先，用户意志压过一切
2. 规则引擎（rules.match，按 priority 降序，同优先级按 id 稳定排序）
3. 扩展名映射（EXT_CATEGORY，13 类全覆盖） confidence 0.90
4. 文件名关键词（KEYWORDS）             confidence 0.70
5. 兜底「其他」                        confidence 0.30
```

设计要点：

- **用户偏好置顶且置信度最高（0.95）**。理由：规则是「我们认为」，偏好是「用户说过」。系统一旦被纠正过，就不应该再犯同一个错。偏好发生在文件名/扩展名粒度上，不污染其它文件。
- **规则优先于纯扩展名映射**。规则能表达「扩展名 + 其它条件」的组合（AND 语义），比如 `setup.exe` 虽然扩展名是 exe，但它是安装包而不是程序本体；`微信截图_1.png` 虽然扩展名是 png，但它比普通图片更可能被用户当下需要。
- **扩展名映射是主力**。它覆盖面最广、歧义最小，0.90 的置信度足以直接执行（高于 HIGH 阈值 0.80 和 MEDIUM 阈值 0.55）。
- **关键词只做辅助**。中文文件名语义弱、误命中率高（「报告」可能出现在任何下载文件里），所以给 0.70——仅高于 MEDIUM 阈值，能过自动归类线但不被视为高可信。
- **兜底明确承认无知**。「其他 / 0.30」不是分类结果，而是一个信号：告诉下游「我不知道，请人来定」。planner 会因此把它降级并产出 warning。

内置三条规则（`DEFAULT_RULES`，可 JSON 序列化）：

| id | 匹配条件 | 目标 | 重要度 | 置信度 | priority |
|---|---|---|---|---|---|
| `rule-screenshot` | 文件名含「截图 / screenshot」 | 图片 | high | 0.85 | 90 |
| `rule-installer` | 扩展名 exe/msi/msix/appx **且** 名含 setup/install/安装 | 安装包 | low | 0.85 | 80 |
| `rule-fresh-archive` | 扩展名 zip/7z/rar **且** 修改时间 ≤ 3 天 | 压缩包 | medium | 0.80 | 60 |

**规则的合并语义**：`merge_rules(DEFAULT_RULES, store_rules)` —— 同 id 覆盖，新 id 追加，结果再按 `(priority 降序, id 升序)` 排序。排序里带 id 是为了**保证结果稳定**：当两条规则同优先级时，命中顺序不能依赖字典/文件读取顺序，否则同样的输入今天和明天可能给出不同答案。

## 3. 重要度判定依据

重要度决定文件进 `重要 / 常用 / 归档` 哪个子目录（`IMPORTANCE_DIRS`）。

```
high   ← 高价值类别（文档/表格/演示/PDF/代码） 且 最近 7 天内修改过
medium ← 常用扩展名（doc/docx/xls/xlsx/ppt/pptx/pdf/jpg/png/mp4/zip/py/js/json/txt/md/csv/gif 等）且 30 天内修改过
low    ← 其余
```

- **为什么用「类别 × 时效」而不是单一维度**：单看类别会把三年前的合同也放进「重要」，单看时效会把下载的临时 png 也放进「重要」。两者相乘才接近用户直觉——「我最近在改的、且是正式产出物」。
- **7 天 / 30 天两个断点**：7 天覆盖「本周正在处理」，30 天覆盖「这个月还在用」。再往外推（90 天）边际信息量急剧下降，且会让归档区几乎吞掉所有文件。
- **未知 mtime 不猜**：`age_days()` 对无有效 mtime 返回 `None`，此时不满足任何时效条件，落到 `low`。宁可归档也不误判成「重要」——归档区用户可以再翻，误判重要会污染用户当前工作视野。
- 规则可以显式指定重要度，覆盖上述推导（见 `rule-screenshot` 无论多老都给 high）。

## 4. 置信度阈值依据

阈值定义在 `constants.py`（冻结）：`CONFIDENCE_HIGH = 0.80`，`CONFIDENCE_MEDIUM = 0.55`。

| 来源 | 置信度 | 与阈值的关系 |
|---|---|---|
| 用户偏好 | 0.95 | 远高于 HIGH — 直接执行，不再询问 |
| 扩展名映射 | 0.90 | 高于 HIGH — 直接执行 |
| 规则命中 | 0.80~0.85 | 处于/高于 HIGH — 直接执行 |
| 文件名关键词 | 0.70 | 介于 MEDIUM 与 HIGH 之间 — 可执行，但属于「可能对」 |
| 兜底「其他」 | 0.30 | 低于 MEDIUM — 降级 + 提示人工确认 |

- **0.55 这条线的作用**：planner 中 `confidence < CONFIDENCE_MEDIUM` 的条目会被强制改判为 `其他 / 归档`，并计入 `Plan.warnings`（「N 个文件置信度低，建议人工确认」）。把 0.30 放在线下方、0.70 放在线上方，意味着**只有「纯猜测」会被拦下**，而「关键词命中」仍然允许自动整理——因为它的错误代价小（放错类别，用户下次改判一次就能学会）。
- **0.80 这条线的作用**：标记「无需人工复核」的分界。目前 planner 只用 `MEDIUM`；`HIGH` 留给后续 UI 做「高置信直接放置 / 中置信逐条确认」的分流。
- **阈值不允许硬编码在模块里**，一律从 `constants.py` 取，避免两个模块对「低置信」理解不一致。

## 5. 改判学习的沉淀机制

目标：用户纠正一次，系统记住；纠正两次，升格为强偏好并能导出为规则。

```
用户改判
   └─> store.remember(item, proposal, user_choice)
         ├─ 写 ext_overrides[.png] 或 name_overrides[文件名]（有扩展名按扩展名，反之按文件名）
         ├─ count += 1
         └─ save()（原子写：先写 .tmp，再 os.replace）

下次 classify
   └─> store.lookup(item) 命中 → confidence 0.95，reasons 含「沿用你的历史选择」

沉淀为规则
   └─> store.export_rules() → count >= 2 的偏好导出为 Rule(ext_in=[".png"], confidence=0.95, priority=100)
```

关键设计：

- **首次是弱偏好（0.90），第二次升强偏好（0.95）**。单次改判可能是手滑或特例，两次以上才视为稳定意愿。`STRONG_COUNT = 2` 就是这个含义。
- **查找顺序 name 优先于 ext**。文件名比扩展名更具体：「这个客户的合同.pdf 放重要」不应该让所有 pdf 都变重要。
- **偏好不覆盖规则，而是排在规则之前**。二者都是「用户意志的延伸」，但偏好粒度更细、证据更直接，所以优先。
- **导出的规则优先级 100**，高于所有内置规则（最高 90），确保用户沉淀的规则不会被内置规则抢走命中。
- **`data/preferences.json` 是唯一持久化位置**，坏了也不致命：解析失败时把原文件复制成 `.bak` 并从空状态重来，比让工具起不来好。用户的整理数据在磁盘上，偏好只是加速器。

## 6. 计划生成（planner）的取舍

- **纯计算，零 IO**。`build_plan()` 不读磁盘、不碰文件，所有判断基于传入的 `FileItem`。好处：可单测（测试全部用构造的 FileItem + sandbox 临时路径）、可预览、可在写入前整体展示给用户确认。
- **已在目标目录则不出 action**。用 `normcase(abspath(...))` 比较，Windows 下大小写不敏感这个差异必须吃掉，否则会出现「原地移动到自己」这种无意义动作。
- **`dst` 填绝对路径**，`target_dir` 填相对路径 `类别/重要`。前者给执行器直接用，后者给 UI 展示用——两种消费者两种粒度，不由 CLI 二次拼接，避免路径拼接逻辑散落两处。
- **降级在后、提示在上**：低置信条目先统一改判为 `其他/归档`，再在 `Plan.warnings` 汇总成一句人话。不逐条刷 warning，是因为用户看到 50 条同一类型提示等于没提示。
- **reason 去重**：`_reason()` 拼接 `reasons` 与 `rule_id` 后会检查是否已包含该 id。早期 demo 出现过「命中规则 rule-installer；规则 rule-installer」的重复文本，已加回归测试 `test_rule_reason_is_not_duplicated` 锁死。

## 7. 风险与已知限制

1. **扩展名映射的静态性**：新文件格式（如 `.avif`、`.webp` 之外的图像格式）需要人工补充映射，不会自动学习。下落为「其他」，代价是可接受的功能缺失而非错误归类。
2. **关键词误判**：中文关键词如「报告」「安装」在文件名中歧义较大，当前给 0.70 中等置信，仍会自动归类。若实测误判偏多，应降级为「仅作为扩展名判定的消歧信号，不单独决定类别」。
3. **规则无法表达否定/正则**：`MATCHER_KEYS` 只有 `ext_in / name_contains / size_gt / age_days_lt` 四种，AND 组合。刻意的限制：规则要能被普通用户读懂和手改，正则能力会让 `preferences.json` 变成程序员的领地。复杂需求交给偏好学习。
4. **`store` 的并发**：单进程工具，未加文件锁。若未来出现多实例同时写 `preferences.json`，`os.replace` 能保证不出现半截文件，但「后写覆盖先写」仍会丢一次记忆。届时需要加锁或改用追加式日志。
5. **性能未实测**：复杂度约 O(文件数 × 规则数)，规则数是个位数量级，预计万级文件在百毫秒内，但**没有实测数据**，属未验证项。
6. **不下结论的部分**：本模块只产出计划，不判断「是否应该移动」。搬到真实桌面时若用户只想预览，`build_plan` 天然支持；是否落盘由 CLI/executor 决定。
